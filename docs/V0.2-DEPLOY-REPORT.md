## 4. 部署中实际修掉的三个坑

这三个都是**本地全绿、一到 Docker 构建才炸**的类型。

### 坑 1 · Dockerfile `ARG` 作用域（最耗时，也最误导）

```dockerfile
ARG APK_MIRROR=https://mirrors.aliyun.com   # 声明在 FROM 之前
FROM node:22-alpine AS base
RUN sed -i "s|x|${APK_MIRROR}|g" ...        # 这里展开成空字符串！
```

`FROM` 之前的 `ARG` 只对 `FROM` 行可见。`RUN` 里拿到的是**空字符串**，且不报错。
后果是包源被改写成 `/alpine/v3.24/main`（协议和主机名都没了），apk 报：

```
WARNING: opening /alpine/v3.24/main/x86_64/APKINDEX.tar.gz: No such file or directory
ERROR: unable to select packages: libc6-compat (no such package)
```

**看起来完全是网络问题。** 我第一次就这样误判了，还做了「同一条命令在 `docker run` 里能成功」
的对照测试 —— 但那个对照无效，因为命令行里我手写了完整 URL，根本没经过 ARG 展开。

修法：在 `base` 阶段内重新声明一次 `ARG APK_MIRROR`（不带默认值即继承全局默认）。

> ⭐ **附带教训（比这个坑更值得记）**：定位时我用 `grep -E "ERROR|DONE|..."` 过滤构建日志，
> 恰好把那两行关键 `WARNING` 过滤掉了，于是在「网络问题」这个错误方向上多花了两轮。
> **过滤构建日志之前，先完整读一遍失败步骤的原始输出。**

### 坑 2 · Alpine 官方源在国内 ECS 上慢到像死锁

同一份 `APKINDEX.tar.gz`，从这台 ECS 实测：

| 源 | 耗时 |
|---|---|
| `dl-cdn.alpinelinux.org` | **12 s+**（卡在超时边缘） |
| `mirrors.aliyun.com` | **0.09 s** |

差 100 倍以上。表现是 `apk add` 卡住数分钟、**没有任何输出**，很像构建死锁。
修法：新增 `APK_MIRROR` build arg（默认官方源，保持镜像可移植），`.env` 里覆盖为阿里云。

### 坑 3 · `.dockerignore` 排除 `tests/` 打穿了 `scripts/`

```
scripts/verify-v02.ts(38,8): error TS2307:
  Cannot find module '../tests/helpers/document-fixtures'
```

`next build` 按 tsconfig 的 `include` 做**全项目**类型检查；`.dockerignore` 排除了 `tests/`，
而 `scripts/verify-v02.ts` import 了其中的夹具 → 构建上下文里解析不到 → 构建失败。
本地 `npm run build` 一切正常，**这个错只在 Docker 构建时暴露**。

修法：把 `scripts` 也加进 `.dockerignore`（它是宿主上的验收工具，本来就不该进镜像）。
**不能**为了让它通过就把 `tests/` 放回上下文 —— 那会把测试代码和夹具打进镜像。

## 5. 另外两处主动加固

### 5.1 构建期 Node 堆上限

这台机器上跑着 ULTRON 的 11 个生产容器。构建实测把 `load average` 推到 **75**（2 核机器），
可用内存一度只剩 451 MB。

加 `ARG NODE_OPTIONS=--max-old-space-size=1536`（仅 builder 阶段）作为保险。
事后确认：**11 个容器全程存活、swap 0 使用**。高负载主因是 `npm ci` 解压几万个小文件的
IO 等待，不是内存 —— 这也说明「SSH 连不上 ≠ 机器挂了」，构建期间出现的 banner 超时是正常的。

### 5.2 镜像 tag `0.1.0` → `0.2.0`

同一 tag 挂不同内容在服务器上排障时非常难受，而且保留上一版镜像就是现成的回滚目标。

## 6. ⛔ 唯一的阻塞项：DNS

```
supplier.ultron.xin @ 223.5.5.5  ->  Non-existent domain
supplier.ultron.xin @ 8.8.8.8    ->  Non-existent domain
（对照：ultron.xin / www.ultron.xin 均正确指向 39.108.235.240）
```

没有解析记录，Let's Encrypt 的 HTTP-01 挑战无法从公网完成。

### 需要做的

在域名解析处添加：

```
supplier.ultron.xin    A    39.108.235.240
```

### 然后一条命令完成 Step 1

```bash
# 建议先演练（链路上的问题在演练里暴露，别去撞 ACME 限额）
sudo bash /srv/suppliercheck/deploy/scripts/enable-https.sh --email <你的邮箱> --staging

# 演练通过后签发正式证书
sudo bash /srv/suppliercheck/deploy/scripts/enable-https.sh --email <你的邮箱> --prod
```

脚本会依次做：校验 DNS 指向本机 → 校验阶段一配置在位 → **实测 HTTP-01 路径可达
（不消耗 ACME 配额）** → certbot 签发（带 `--deploy-hook`，续期后自动 reload）
→ 渲染 443 配置替换阶段一 → `nginx -t` 失败**自动回滚** → reload → 端到端验证。

**已实测该脚本的 DNS 闸门有效**：当前运行会在第 1 步直接退出（exit 1），
输出「请先添加 A 记录」，不触碰任何东西。

> 注意：这台机器上 certbot **只有 staging 账号**（`acme-staging-v02`），
> 没有生产账号。首次正式签发会新注册一个生产账号，所以 `--email` 是必填的。

## 7. ⚠️ 发现但未处理的既有隐患（只报告，属其他服务）

**`ultron.xin` 的 Let's Encrypt 证书没有任何续期机制。**

| 证据 | 结果 |
|---|---|
| `/etc/letsencrypt/renewal/` | 空 |
| `certbot certificates` | `No certificates found` |
| certbot 账号 | 只有 `acme-staging-v02`，无生产账号 |
| acme.sh | 不存在 |
| 证书文件 | `/etc/nginx/ssl/ultron.xin.le.fullchain.pem`（手工放置） |
| SAN | `ultron.xin, www.ultron.xin`（**无通配符**） |
| 有效期 | 2026-09-08 → **2026-12-07** |

⇒ 该证书**到期后不会自动续**，ULTRON 生产站会直接挂。

按「发现冲突先报告、不自行处理」的约定，**我没有动它**。建议单独安排一次处理
（顺带一提：给 `supplier.ultron.xin` 签发后，certbot 的自动续期机制会正常建立，
那条路径反而是健康的）。

另外：因为现有证书 SAN 里**没有通配符、也没有 supplier 子域**，所以
`supplier.ultron.xin` **无法复用**它，必须单独签发 —— 这也确认了 Step 1 不可省略。
