## 4. 过程中实际修掉的问题

### 4.1 构建期（本地全绿、一进 Docker 就炸）

**坑 1 · Dockerfile `ARG` 作用域（最耗时，也最误导）**

```dockerfile
ARG APK_MIRROR=https://mirrors.aliyun.com   # 声明在 FROM 之前
FROM node:22-alpine AS base
RUN sed -i "s|x|${APK_MIRROR}|g" ...        # 这里展开成空字符串！
```

`FROM` 之前的 `ARG` 只对 `FROM` 行可见，`RUN` 里拿到的是**空字符串**，且不报错。
后果是包源被改写成 `/alpine/v3.24/main`（协议和主机名都没了）→ apk 报
`opening /alpine/v3.24/main/x86_64/APKINDEX.tar.gz: No such file or directory`。
**看起来完全是网络问题。** 我第一次就这样误判，还做了「同一条命令在 `docker run` 里能成功」
的对照 —— 但那个对照无效，因为命令行里我手写了完整 URL，根本没经过 ARG 展开。

> ⭐ **附带的教训比这个坑更值钱**：定位时我用 `grep -E "ERROR|DONE|..."` 过滤构建日志，
> 恰好把两行关键 `WARNING` 过滤掉了，于是在错误方向上多花了两轮。
> **用 grep 过滤构建日志之前，先完整读一遍失败步骤的原始输出。**

**坑 2 · Alpine 官方源在国内 ECS 上慢到像死锁**

| 源 | 取同一份 `APKINDEX.tar.gz` 耗时 |
|---|---|
| `dl-cdn.alpinelinux.org` | **12 s+**（卡在超时边缘） |
| `mirrors.aliyun.com` | **0.09 s** |

表现是 `apk add` 卡住数分钟、**没有任何输出**，很像构建死锁。新增 `APK_MIRROR` build arg 解决。

**坑 3 · `.dockerignore` 排除 `tests/` 打穿了 `scripts/`**

```
scripts/verify-v02.ts(38,8): error TS2307:
  Cannot find module '../tests/helpers/document-fixtures'
```

`next build` 按 tsconfig 的 `include` 做**全项目**类型检查，而 `scripts/verify-v02.ts`
import 了被排除的测试夹具。本地 `npm run build` 一切正常，**只在 Docker 构建时暴露**。
修法：把 `scripts` 也加进 `.dockerignore`（它是宿主上的验收工具，本就不该进镜像）。

### 4.2 证书签发期

**坑 4 · `http2 on;` 在旧版 nginx 上是硬失败**

```
[emerg] unknown directive "http2" in /etc/nginx/conf.d/suppliercheck.conf:40
nginx: configuration file /etc/nginx/nginx.conf test failed
```

`http2 on;` 是 nginx **≥ 1.25.1** 的新语法；这台是 **1.22.1**，直接用 `[emerg]` 拒绝加载
整份配置 —— 不是警告，是硬失败。已改用兼容写法 `listen 443 ssl http2;`
（新版只产生 deprecation warning，兼容面更广）。

> ✅ **这里要表扬一下自己写的回滚**：`nginx -t` 一失败，脚本立刻把配置还原、重新校验、
> 再退出 —— **生产服务零影响，也没有出现「配置坏掉但已 reload」的最坏情况**。

**坑 5 · Let's Encrypt 二次校验偶发超时**

第一次签发失败：

```
Type:   connection
Detail: During secondary validation: 39.108.235.240: Fetching
        http://supplier.ultron.xin/.well-known/acme-challenge/...:
        Timeout during connect (likely firewall problem)
```

`During secondary validation` 这个前缀很关键 —— 它说明**主校验是通过的**，
只是 LE 从全球额外节点校验时有节点超时。

**没有先去改安全组**，而是做了多地域实测。用 `check-host.net`（免注册、有 JSON API）：

| 测试 | 结果 |
|---|---|
| `check-tcp` 80 端口（12 节点） | 全部 OK，含 us1/us2/us4、ca1、fi1 |
| `check-http` ACME 路径（20 节点） | **全部 OK / HTTP 200**，含美、英、德、荷、瑞典、日、俄 |

⇒ 确认是 **LE 侧的瞬时抖动**，不是本机防火墙。**直接重试，第二次成功。**

（失败配额是「每账号 + 每域名 + 每小时 5 次」，重试一两次非常安全。）

## 5. 另外两处主动加固

### 5.1 构建期 Node 堆上限

这台机器上跑着 ULTRON 的 11 个生产容器。构建实测把 `load average` 推到 **75**（2 核机器），
可用内存一度只剩 451 MB。加 `ARG NODE_OPTIONS=--max-old-space-size=1536`（仅 builder 阶段）作为保险。

事后确认：**11 个容器全程存活、swap 0 使用**。高负载主因是 `npm ci` 解压几万个小文件的
IO 等待，不是内存 —— 所以「构建期间 SSH 连不上 ≠ 机器挂了」，那只是 banner 超时。

### 5.2 镜像 tag `0.1.0` → `0.2.0`

同一 tag 挂不同内容在服务器上排障时非常难受，且保留上一版镜像就是现成的回滚目标。
