## 3. 数据模型（新增）

```
suppliers          供应商主体。部分唯一索引 (workspace_id, name) WHERE deleted_at IS NULL
review_templates   自定义审核模板。同上约束；config 为 jsonb
review_runs        一次审核。含 template_snapshot jsonb、summary jsonb、状态机、引擎身份
review_findings    一条发现。含 rule_id / severity / source / evidence / locator jsonb
documents          + supplier_id（新字段，set null）
```

关键设计：

1. **`template_snapshot` 整份存库。** 模板改了以后，历史报告的含义不能跟着漂移 —— 报告里展示的是发起那一刻的模板。
2. **`source` 区分 `RULE` / `AI`。** 报告页把两类结论分开呈现，AI 结论单独标注来源。
3. **`engine_provider / engine_model / engine_mock` 在**执行完成时**回写，不是创建时。** 任务可能在入队后几分钟才跑，中间配置可能被改；"这份报告是谁产的"必须记准。
4. **部分唯一索引表达「同名只允许存在一个未删除的」**，配合软删除，让"删了再建同名"可行。

## 4. 审核引擎

### 4.1 形态

纯函数 + 正则 + 标准算法。**不联网、不调模型、不读系统时钟**（`now` 由调用方传入，测试用固定日期）。同样的输入必然产出同样的发现。

### 4.2 15 条规则

| # | 规则 id | 界面名 | 类别 | 默认级别 |
|---|---|---|---|---|
| 1 | REQUIRED_DOCUMENT_MISSING | 必备资料缺失 | 完整性 | HIGH |
| 2 | OPTIONAL_DOCUMENT_MISSING | 非必备资料缺失 | 完整性 | INFO |
| 3 | PLACEHOLDER_CONTENT | 存在未填写的占位内容 | 完整性 | MEDIUM |
| 4 | DOCUMENT_NOT_READY | 资料尚未完成解析 | 可读性 | HIGH |
| 5 | DOCUMENT_UNREADABLE | 资料无可提取正文 | 可读性 | HIGH |
| 6 | DOCUMENT_TEXT_TRUNCATED | 资料正文被截断 | 可读性 | INFO |
| 7 | USCC_MISSING | 未找到统一社会信用代码 | 主体 | MEDIUM |
| 8 | USCC_INVALID | 统一社会信用代码校验位错误 | 主体 | HIGH |
| 9 | USCC_MULTIPLE | 出现多个不同主体代码 | 主体 | MEDIUM |
| 10 | COMPANY_NAME_CONFLICT | 疑似存在多个企业主体 | 主体 | MEDIUM |
| 11 | SUPPLIER_NAME_NOT_FOUND | 资料中未出现申报主体名称 | 主体 | LOW |
| 12 | CERTIFICATE_EXPIRED | 证照已过期 | 有效期 | **CRITICAL** |
| 13 | CERTIFICATE_EXPIRING_SOON | 证照即将到期 | 有效期 | HIGH |
| 14 | CERTIFICATE_EXPIRY_UNKNOWN | 有效期无法判定 | 有效期 | LOW |
| 15 | AMOUNT_MISMATCH | 金额大小写不一致 | 一致性 | HIGH |

`enabledRules` 为空集合 = **全部执行**（不是"全部不执行"）。理由：一次什么都没查却显示"已完成"的审核，是最危险的产物。

### 4.3 三条写规则的硬纪律（写在 `lib/reviews/rules.ts` 文件头）

1. **不制造假阳性。** 无法唯一确定时不下结论，而不是给一个"大概"的结论。
2. **错误代价不对称。** 漏掉一个问题 vs 冤枉一份合格资料，后者代价更高 —— 它会训练用户忽略告警。能确定的报高等级，不确定的报低等级或干脆不报。
3. **详情里必须写清判定依据。** 每条发现的 `detail` 都要说明"查了什么、查了哪些资料、用什么关键词"。看不懂为什么被报，等于没有这条规则。

### 4.4 四个假阳性治理实例（我认为最值得审的地方）

| 场景 | 天真的写法 | 本项目的取舍 |
|---|---|---|
| 中文大写金额解析 | 「万元整」这类单位残片解析成 `0` | 末尾 `return value > 0 ? value : null`。解析成 0 会造出**完全虚构的**「大小写不一致」指控 |
| 金额配对 | 全文任意两个金额互相比对 | 只在 120 字符窗口内取**距离最近**的一个小写金额；配不上就不报 |
| 企业名抽取 | 正则直接抓 `...有限公司` | 加左边界捕获组。不加会抓出「与甲公司有限公司」这种**粘连名**——漏一个名字只是少一条提示，编一个名字会写进报告 |
| 有效期窗口 | 从「有效期」往后取定长前瞻 | 右端取 `min(定长前瞻, 下一个"有效期"下标, 文本末尾)`；「至/到/截止+日期」取**第一个**而非最后一个。否则三张证书各占一行时，第一行会看见后面所有日期，三张都按最后一张判定 |

### 4.5 「不制造假 AI」

- Provider 是 mock 时：`ai.enabled = false`，产出 3 条说明，覆盖度说明里写明「AI 复核未启用」；**不产生任何 AI 类别的发现**。
- 非 mock 时才产出 `AI` 类别发现，且 severity **封顶 MEDIUM**（只作提示，不作定性）。
- 真实 Provider 返回空结论时记「未返回结论」，**不补一句「未发现异常」**。

### 4.6 覆盖度诚实

`buildCoverageNotes` 逐条列出：未解析完成 / 无可用正文 / 正文被截断 / 字符预算用尽 / 规则执行异常已跳过 / 模板跳过 / AI 未启用。
目的很具体：让「查过了没问题」和「根本没查」在界面上是两件不同的事。

### 5.1 授权唯一入口 `lib/auth/action-context.ts`（全文件，55 行）

```ts
import "server-only";

import { ensureWorkspaceForUser } from "@/lib/auth/workspaces";
import { requireUser, requireWorkspaceAccess, type WorkspaceContext } from "@/lib/auth/guards";
import type { WorkspaceRole } from "@/lib/db/schema";
import { ERROR_CODES, toAppError } from "@/lib/errors";
import { logger } from "@/lib/logger";

/**
 * Server Action / 页面共用的授权入口。
 *
 * 为什么要在 requireWorkspaceAccess 之外再包一层：
 * 每个动作都需要同样的三步 ——「要登录 → 找当前工作区 → 校验成员资格」。
 * 散在十几个 action 里写的后果不是"重复"，而是**迟早有一个漏掉其中一步**，
 * 而漏掉的那个就是越权入口。授权路径只允许有一条。
 *
 * 默认要求 MEMBER（可读可写）。只读场景显式传 "VIEWER" ——
 * 默认值选宽的那个是刻意的：宁可让人多写一个参数，也不要因为忘了传而放松权限。
 */
export async function requireActionWorkspace(
  minimumRole: WorkspaceRole = "MEMBER",
): Promise<WorkspaceContext> {
  const user = await requireUser();
  const active = await ensureWorkspaceForUser(user.id);
  return requireWorkspaceAccess(active.id, { minimumRole });
}

/** 只读页面用。语义上等于「已登录且属于该工作区」。 */
export async function requireReadableWorkspace(): Promise<WorkspaceContext> {
  return requireActionWorkspace("VIEWER");
}

/**
 * 执行一个动作，**只容忍「目标已不存在」这一种失败**。
 *
 * 为什么不一概 try/catch 吞掉：那会把认证失效、权限不足、数据库不可用
 * 一起变成"界面没反应"，是最难排查的一类故障。
 * 而「目标已不存在」是真实存在的一种并发场景 —— 同一个人在另一个标签页里
 * 刚把这条记录删掉，这边再点一次删除按钮。此时**正确行为就是什么都不做**，
 * 随后的列表刷新会自然反映出真实状态，报一个错误页反而是错的。
 */
export async function runTolerantOfMissing(
  work: () => Promise<void>,
  context: Record<string, unknown>,
): Promise<void> {
  try {
    await work();
  } catch (error) {
    const appError = toAppError(error);
    if (appError.code !== ERROR_CODES.NOT_FOUND) {
      throw error;
    }
    logger.warn("操作目标已不存在，按幂等处理", { ...context, code: appError.code });
  }
}
```

### 5.2 归一化 + 统一社会信用代码校验 `lib/reviews/extract.ts`

```ts
export function normalizeForMatch(text: string): string {
  let out = "";
  for (const char of text) {
    const code = char.codePointAt(0) ?? 0;
    if (code >= 0xff01 && code <= 0xff5e) {
      out += String.fromCharCode(code - 0xfee0);   // 全角 ASCII → 半角
      continue;
    }
    out += EXTRA_FULLWIDTH_MAP[char] ?? char;
  }
  return out;
}

export function validateUscc(rawValue: string): UsccValidation {
  const code = rawValue.trim().toUpperCase();
  if (code.length !== 18) {
    return { valid: false, reason: `长度应为 18 位，实际 ${code.length} 位` };
  }
  const illegal = [...code].find((char) => !USCC_ALPHABET.includes(char));
  if (illegal) {
    return { valid: false, reason: `含非法字符「${illegal}」（该字符不在 GB 32100 字符集内）` };
  }

  let sum = 0;
  for (let i = 0; i < 17; i += 1) {
    sum += USCC_ALPHABET.indexOf(code[i] as string) * (USCC_WEIGHTS[i] as number);
  }
  const remainder = 31 - (sum % 31);
  const expected = USCC_ALPHABET[remainder === 31 ? 0 : remainder];

  if (expected !== code[17]) {
    return { valid: false, reason: `校验位应为「${expected}」，实际为「${code[17]}」` };
  }
  return { valid: true };
}
```

**不变式：归一化后长度必须与原文一致。** 因为发现的 `evidence`（原文摘录）下标是在归一化副本上算出来的，一旦长度漂移，摘录就会指向错误的位置 —— 那不是"显示不好看"，是**假证据**。这条不变式有专门的单测盯着。

 * 金额大小写一致性。
 *
 * ⚠️ 这条规则最容易写成假阳性发生器，所以做了两处克制：
 *
 * 1. **只在窗口内配对**。「小写 ¥175,000.00 大写 壹拾柒万伍仟元整」是相邻的；

evaluate: (context) =>
  readableDocuments(context.documents).flatMap<DraftFinding>((document) => {
    const chinese = findChineseAmounts(document.text);
    if (chinese.length === 0) return [];
    const small = findSmallAmounts(document.text).filter(
      (hit): hit is typeof hit & { value: number } => hit.value !== null,

      if (cn.value === null) continue;
      const near = small.filter((hit) => Math.abs(hit.index - cn.index) <= AMOUNT_PAIR_WINDOW);
      if (near.length === 0) continue;

      if (Math.abs(nearest.value - cn.value) <= 0.01) continue;

### 5.4 发现数上限与覆盖度说明 `lib/reviews/engine.ts`

```ts
/**
 * 发现数上限。
 *
 * 超限时**先截断再如实告知**，而不是截断后假装这就是全部。
 * 「报告只显示了前 500 条」与「只有 500 条问题」是两件完全不同的事。
 */
function applyFindingCap(
  findings: DraftFinding[],
  maxFindings: number | undefined,
): { findings: DraftFinding[]; truncationNote: string | null } {
  if (maxFindings === undefined || findings.length <= maxFindings) {
    return { findings, truncationNote: null };
  }
  const kept = findings.slice(0, maxFindings);
  const dropped = findings.length - kept.length;
  return {
    findings: kept,
    truncationNote: `本次共产生 ${findings.length} 条发现，已按严重级别保留前 ${maxFindings} 条，其余 ${dropped} 条未展示。`,
  };
}

/**
 * 覆盖度说明。
 *
 * 存在的唯一理由：让使用者一眼看出「这次结论是在多少资料上得出来的」。
 * 一份只覆盖了 3/10 份资料的报告如果看起来和全覆盖的报告一模一样，
 * 那它就是在误导 —— 这类"沉默的失真"比报错危险得多。
 */
function buildCoverageNotes(input: BuildSummaryInput, readableCount: number): string[] {
  const notes: string[] = [];
  if (input.documents.length === 0) {
    notes.push("本次审核没有选中任何资料，所有规则都在空集合上执行，结论没有实际意义。");
    return notes;
  }
  // …… 未解析完成 / 无可用正文 / 正文被截断 / 一条都没读到 / 规则异常 / 模板跳过
  notes.push(...input.aiNotes);   // AI 的说明本质上是同一件事：「这次结论是怎么来的」
  return notes;
}
```

```ts
/**
 * 原子认领一次审核任务。
 *
 * 与文档解析用同一套模式（UPDATE ... WHERE ... RETURNING）而不是「先查后写」：
 * 后者在用户连点两次「重新运行」时会让同一次审核跑两遍，把发现重复写进库里。
 * 超时阈值的作用：进程重启会让任务永远停在 RUNNING，必须有办法重新认领。
 */
export async function claimReviewRun(
  runId: string,
  staleThresholdMs: number,
): Promise<ReviewRun | undefined> {
  const staleBefore = new Date(Date.now() - staleThresholdMs);
  const [row] = await db
    .update(reviewRuns)
    // 生命周期时间戳一律用**数据库时钟**（now()）：createdAt 是数据库默认值，
    // 若 startedAt / finishedAt 用应用时钟，两个时钟差 1 秒就会出现
    // 「完成时间早于发起时间」的报告 —— 那只是时钟漂移，但用户会以为结论不可信。
    .set({ status: "RUNNING", startedAt: sql`now()`, updatedAt: sql`now()` })
    .where(
      and(
        eq(reviewRuns.id, runId),
        isNull(reviewRuns.deletedAt),
        or(
          inArray(reviewRuns.status, ["QUEUED", "FAILED", "READY"]),
          and(eq(reviewRuns.status, "RUNNING"), lt(reviewRuns.updatedAt, staleBefore)),
        ),
      ),
    )
    .returning();
  return row;
}
```

### 5.6 发现排序（本轮实测抓到的一个真 bug，已修）

```ts
/**
 * ⚠️ 严重级别必须**降序**（desc）。Postgres 的 enum 排序按声明顺序，
 * 而本项目的声明顺序是 INFO → LOW → MEDIUM → HIGH → CRITICAL，
 * 直接 orderBy(severity)（升序）会把「严重」排在最后 —— 报告一打开先看到提示、
 * 最后才看到阻断项，这跟任何人的阅读预期都是反的。
 */
export async function listRunFindings(runId: string): Promise<ReviewFinding[]> {
  return db
    .select()
    .from(reviewFindings)
    .where(eq(reviewFindings.reviewRunId, runId))
    .orderBy(
      desc(reviewFindings.severity),
      reviewFindings.createdAt,
      reviewFindings.ruleId,
      reviewFindings.title,
    );
}
```

这个 bug 是**看渲染出来的报告时发现的**（不是靠读代码）：原实现 `orderBy(severity)` 是升序。我随后直接查库实测确认了方向：

```
ASC : LOW < LOW < HIGH < HIGH < HIGH
DESC: HIGH > HIGH > HIGH > HIGH
```

### 11.1 【真·已修】有效期「长期」语义 —— 本轮最严重的一条

**Gemini 的说法**：中国营业执照、开户许可证上大量写「长期」「永久」「***」「——」，会被一律判成"无法判定有效期"。

**核实**：属实。原来的 `findExpiryWindows` 只找日期，找不到日期就把这个窗口丢给 `CERTIFICATE_EXPIRY_UNKNOWN`。后果不是"多一条告警"，而是**每一份合法执照都被标黄，进而淹没真正需要人工看的相对期限**——这跟我自己在第 6 节写的"错误代价不对称"直接冲突。

**修复**：`lib/reviews/extract.ts` 新增 `findLongTermMarkers()`。三个取舍：

1. **识别范围**：`长期 / 永久 / 无固定期限 / 不限期 / 不设定`，外加排版占位符 `***`、`——`。
2. **只看标记后 16 个字符，且不越过下一个「有效期」标记**。这条是防误解吸——如果不设边界，`本许可项目长期 Contact...` 后面任意位置出现 `***` 都会被算成"长期"。
3. **长期项不计入未判定计数，但要在 detail 里交代数量**。沉默地少报同样是失真。

**测试**（`tests/unit/reviews-engine.test.ts:735-756`）：6 种写法逐个验证，外加一条混合用例 `营业执照有效期：长期 / ISO 9001 有效期至 2026-10-05` —— 只对真日期判定，详情里说明长期项数量。

### 11.4 【真·已修】`runTolerantOfMissing` 被误用在变更类动作上

**Gemini 的说法**：这个函数对"更新/变更"类动作不适用。

**核实**：属实，而且实际影响比他描述的更直接——`app/actions/suppliers.ts` 里的 **archive / restore / assign** 三处都走了这个包装。用户点了"归档"，目标行因为已被别人删掉而查不到，函数吞掉 NOT_FOUND 返回 `{ ok: true }`，界面提示"操作成功"，而实际上什么都没发生。**静默失败，且带成功反馈**——这是最坏的一类。

**修复**：

- 函数重命名 `runTolerantOfMissing` → **`runIdempotentDelete(deleteWork, context)`**。
- 参数名刻意叫 `deleteWork`：让它在别处用的时候读起来就是错的。这是刻意的"用不下去"设计。
- archive / restore / assign 改为直接调用并加注释说明为什么这三个不走幂等。
- **只保留 delete**（双点归档一致 = 幂等是语义要求，不是偷懒）。

原则一句话：**幂等是删除的语义，不是所有写操作的兜底。**

是**分批批量**，不是单条。而且本轮把 CHUNK 从 100 提到 500，往返次数反而降到原来的 1/5。

### 11.9 【驳回】「`claimReviewRun` 返回 Date 有序列化风险」

**依据**：`claimReviewRun` 的返回值**只在同一个 Server Action 进程内**传给 service 层和日志，从不跨 Server Action / RSC 边界返回给客户端。`reviewFindings` 里的时间戳用的是数据库时钟 `sql\`now()\``。

（顺带说明本轮另一个已修的真 bug：`startedAt` / `finishedAt` 原来用 `new Date()`，而 `createdAt` 用 DB 时钟，出现过**"完成时间早于发起时间"**。现在三处统一用 `sql\`now()\``。）
