### 被移除的两个（都是实测后否掉的，不是偏好）

| 包 | 移除原因 |
| --- | --- |
| `exceljs` 4.4.0（23 MB + 40 传递依赖） | `WorkbookReader` 流式读取**依赖 zip 条目顺序**：遇到 `xl/workbook.xml` 排在最后时会崩（`Cannot read properties of undefined (reading 'sheets')`）。而 Excel 自己写出的文件正是这个顺序。逐层探测确认是 `_parseWorksheet` 早于 workbook.xml 触发，`this.model` 仍为 undefined。改为 `yauzl + saxes` 自建两遍式解析器，夹具刻意把 workbook.xml 放最后作为回归保护 |
| `mammoth` 1.12.3 | `lib/unzip.js` 里 `fs.readFile()` 把整份文件读进内存，再叠 JSZip + xmldom DOM，**直接违反内存红线**，另带 10 个传递依赖。改为与 XLSX 共用 `yauzl + saxes`，依赖增量 0 |

## 3. 内存紧张怎么应对

生产宿主是 **2 vCPU / 4 GiB、可用内存约 1.5 GB** 的 ECS，且同时跑着别的生产服务。
所以「不把文件读进内存」是硬约束，不是优化项。

| 阶段/格式 | 处理方式 | 内存特征 |
| --- | --- | --- |
| 上传 | busboy 流式 → 计量 → 直接写私有盘 | 与文件大小无关 |
| ZIP | 先只读中央目录**规划**，再按计划逐条串行解压 | 与包大小无关 |
| DOCX | 按需开条目流 + saxes 流式解析 | 与文件大小无关 |
| XLSX | 两遍遍历（元数据 → 逐行），受行数/单元格/共享串字符数上限约束 | 与文件大小无关 |
| PDF | `unpdf`，**唯一整份读入的格式** | 见下 |

**关于 PDF 这个例外的处理（不是掩盖，是明确约束）：**

1. 单文件上限 20 MB，且 `ABSOLUTE_MAX_UPLOAD_BYTES = 50 MB` 硬顶（环境变量配大了也突破不了）；
2. 解析任务**全局串行**（`lib/documents/queue.ts`），峰值 = 单份文件，不是 N 份；
3. 提取文本硬截断 30 万字符，超出标记 `truncated: true` 并如实提示，不静默丢弃。

**其余配套纪律：**

- 所有限额集中在 `lib/documents/limits.ts`；实现里不允许再出现魔法数字，测试直接引用常量。
- 压缩包**七道闸门**：条目数 / 单条目解压后大小 / 整包总量 / 压缩比（>200:1）/ 禁止嵌套 / 禁止加密 / 类型白名单 —— 全部在**解压之前**基于中央目录元数据判断。
- 元数据可以撒谎，所以解压时再用 `InspectionTransform` 按**实际字节数**复核一遍。
- 被拒绝的条目**如实记进计划并展示给使用者**，不是悄悄跳过。

## 4. 多租户隔离怎么应对

授权链路（每一步都不可跳过）：

```
会话（未登录 → 401）
  → 按 id 查库拿到该行自己的 workspace_id
  → requireWorkspaceAccess(该 workspace_id) 回库核对成员关系
  → 通过才开流
```

**本轮做的一处顺序修正（重要）**：按 id 取资源的路由原本是「先查库、再校验权限」，
于是未登录时 `404`（id 不存在）与 `401`（id 存在）**可区分** —— 这本身就是可枚举 id 的信号。
现在统一改成**先 `requireUser()` 再碰数据库**，未登录的答案永远只有一个：401。
已写成冒烟断言（拿一个语法合法但不存在的 UUID 去打 4 个接口 + 上传，全部必须 401）。

**两条语义不同的下载路径，不混用：**

| 路径 | 授权方式 | 用途 |
| --- | --- | --- |
| `/api/files/[documentId]` | 登录会话 + 工作区成员校验 | 界面预览与下载 |
| `/api/files/signed/[token]` | HMAC 签名 + 有效期 **+ 同样要求登录会话** | 短期分享 |

签名 URL **仍然要求登录**是清醒的取舍：签名 URL 一旦被转发就等于给出一次数据访问机会，
而供应商安全问卷、资质证书这类资料本身带保密义务。代价是它不能直接喂给 wget / Nginx X-Accel。

**其他：** 存储路径从不出现在任何响应里（只有 documentId）；列表接口只回元数据与摘要；
下载响应头用 `filename*=UTF-8''` 正确承载中文文件名。

## 6. 过程中发现并修复的缺陷（6 个）

| # | 缺陷 | 怎么发现的 | 修法 |
| --- | --- | --- | --- |
| 1 | `exceljs` 流式读取器崩溃 | 写解析器时单测 | 移除，自建两遍式解析器 |
| 2 | `mammoth` 整份读入内存 | 读源码 + 实测内存 | 移除，复用 yauzl + saxes |
| 3 | **存储键里的 id ≠ `documents.id`** | **端到端** | `createDocument` 的 `id` 改为必填，两边共用同一个 id |
| 4 | **busboy 按 latin1 解中文文件名** | **端到端** | `defParamCharset: "utf8"` |
| 5 | **standalone 切工作目录 → 相对存储路径落进镜像层** | **端到端** | production 下强制绝对路径，启动即拒绝 |
| 6 | saxes 的 `fragment: true` 会拒绝 `<?xml?>` 声明 | 写解析器时单测 | 改用 `{xmlns:false, position:false}`，首块剥 BOM |

第 3、4、5 条值得单独说明：它们**全部逃过了单元测试**。单元测试直接构造 `info` 对象
（绕过 busboy 解码）、直接在项目根跑（进程工作目录没变）、不检查磁盘文件名与库中 id 的关系。
这正是端到端验收存在的理由 —— 六层单元测试证明不了「装在一起能转」。

## 9. 已知限制与未验证项（如实登记）

1. **PDF 中文提取未经自动化验证。** 手工合成的 PDF 夹具放不了中文 —— 中文即使以 UTF-16BE
   hex 字符串写进文本层，pdf.js 也会按字体编码（Helvetica → WinAnsi）逐字节映射成乱码，
   因为夹具没有嵌入字体程序与 ToUnicode CMap。真实中文 PDF 自带这些，提取是正常的，
   **但这一点在本项目的自动化测试里没有覆盖**。已留下验证入口：
   ```bash
   REAL_PDF="/path/to/真实中文.pdf" npx vitest run tests/manual
   ```
   顺带：已用两份真实 PDF（`kdp_test/*.pdf`，均为英文）验证过 —— 3 页 / 4 页提取完好，
   无乱码、无替换字符。**投产前请用一份真实中文 PDF 跑一次。**
2. **图片 OCR 不可用。** 接口已抽象（`image` 解析器），当前如实返回
   「暂不支持本地 OCR，待接入外部 API。图片已完整保存，可下载与预览。」不伪造内容。
3. **解析是进程内异步，不是独立 worker/队列服务。** `enqueueDocumentProcessing` 原子认领后
   用 `void runExclusive(...)` 在进程内串行执行。进程重启会丢在途任务，靠
   `STALE_JOB_THRESHOLD_MS`（10 分钟）把僵死的 PROCESSING 重新认领。这是为「不加新服务」
   做的取舍，代价明确。
4. **20 MB 大文件的真实上传未实测。** 限额与流式路径由代码 + 单元测试保证，但没跑过真实大文件。
5. **`archive.ts` 里「条目名包含非法路径片段」这一分支当前不可达。**
   实测 yauzl 在中央目录解析层就拒绝 `..`、反斜杠、绝对路径 —— 整包在解压前就被挡下（400）。
   该分支保留为纵深防御，但**不要误以为它被测试覆盖**。清洗函数本身另有独立测试。
6. **ZIP 内的 `.exe` 等非法类型会被拒绝并记进清单**，但拒绝是「跳过该条目」，整包其余条目照常展开。

## 10. 明确不做的事（取舍记录）

- **不给签名 URL 免除登录。** 见 §4。
- **不为了「支持更多格式」引入重依赖。** `exceljs` 与 `mammoth` 都是实测后移除的。
- **不在解析失败时写入任何占位文本。** 失败就是 `FAILED` + 原因，绝不伪造。
- **不做「猜」。** 图片没有 OCR 就说没有，PDF 提取不到文本层就提示可能是扫描件。
- **不动 V0.1 的核心抽象。** `AIProvider` / `StorageProvider` 只做了加法
  （`uploadStream` / `downloadStream` / `localPathFor?`），既有接口未改签名。
